# 球路画像与对手侦察（Shot-pattern scouting）演进规划

状态：用户已确认方向（2026-11-10）。**目标场景是转播/鹰眼机位视频，手机拍摄和 iOS 应用暂时搁置。**
模型策略：先用公开模型（YOLO、TrackNet 等）加微调；自研模型放到基础完成之后，见
[模型调研与升级路线](../research/2026-11-10-model-landscape.md)。
本文是 [教练智能总规划](2026-09-11-1411-feat-tennis-coaching-intelligence-plan.md) 中
U4（落点关联、回合）和 U5（战术）的细化与延伸，不覆盖其中的证据规则和发布门槛。

## 1. 目标

把每一拍还原成二维球场上的一条“球路”：**谁、在哪里击球、用什么拍型、球落在哪里**，
并按回合顺序串起来。在此之上回答“条件 → 回应分布”类问题，例如：

- 我在一区（deuce）发外角时，他的接发球落在哪里？
- 我把球打到他反手时，他回斜线、直线还是中路？落点深浅如何？
- 他被拉出场外后，下一拍偏好打哪里？

每个答案都给出落点图、方向比例、样本数、置信区间和可回看的片段。

## 2. 关于“3D 转 2D”的技术判断

画球路图和落点图**不需要完整的三维重建**：

- 落点在地面上，地面是一个平面，现有的球场单应矩阵（homography）就能把落地瞬间的
  像素准确换算成球场坐标。
- 击球位置用击球者的脚点（同样在地面上）换算。
- 一拍的球路 = 击球者脚点 → 关联的落点。这与项目规则一致：落点必须有弹跳证据，
  空中的球不能直接投影成落点。

真正的三维轨迹（球高、过网高度、球速、弧线）是后续的可选增强（第 5 节 T7）：
需要相机标定加逐拍物理拟合，并且要单独验证后才能进入事实层。所以整件事的关键
不是 3D 数学，而是**弹跳检测、击球检测、拍与落点的关联**这三件事做准。

## 3. 现状盘点：已有什么、缺什么

| 能力 | 现状 | 对本目标的缺口 |
|---|---|---|
| 球追踪 | YOLO 默认；TrackNet 可选，转播片段上观测率约 85%，无人工标注精度 | 远端球、被遮挡时丢球；记分牌图标、白鞋、场外的球会被误检；没有人工标注精度 |
| 球场标定 | 手动四角 / 14 关键点单应矩阵，坐标系 `far_left_x_right_y_near_m` | 转播镜头会摇移变焦，需要逐帧更新和平滑；回放、特写镜头要识别并跳过 |
| 弹跳检测 | `CandidateDetector` 启发式，未验证 | **最大缺口**：落点是全部战术分析的基础 |
| 击球检测 | `contact-v2` 在 101 个击球窗口中覆盖 96 个，时间精度未验证 | 远端击球可能偏 0.1–0.3 秒；发球抛球误报 |
| 击球者位置 | `positions.py` 脚点投影，`error_m` 为空 | 没有误差评估 |
| 拍型 | 自动结果全部是 unknown，只能人工标五种 | “打他反手”需要正手/反手自动分类和持拍手信息 |
| 拍—落点关联 | `events-v3` 已有 `links`，可审核 | 自动关联逻辑和评估缺失 |
| 回合 | `rallies-v1` 有 `shot_ids` 和 `outcome` | 没有发球方、一区/二区、一发/二发、拍序（发球/接发/第三拍） |
| 选手身份 | 单场内 participant / assignment 已完善 | 没有跨场次的选手档案，无法把同一对手的多场比赛合并 |
| 统计 | `review_statistics.py` 只有计数类指标和落点列表 | **已实现第一版**：`shots.py` 派生球路，`tactics.py` 做“条件 → 回应”查询（见第 5 节） |
| 界面 | 桌面复核 | 命令行可导出球路图；桌面应用里还没有战术筛选页 |

## 4. 新增的数据层

沿用现有分层（观测 → 复核 → 派生 → 洞察）。第一版只新增派生层（`shots-v1`），
不改动与 Swift 共享的事件、回合契约，所以搁置中的 iOS 读取器不受影响。

- **回合上下文**：第一版从已有证据推导，不新增字段。回合第一拍标为发球时，它就是发球，
  第二拍是接发；发球区（一区/二区）由发球者站位在中线的哪一侧决定。一发/二发、比分、
  跨场次的选手档案留到后续（需要改共享契约）。
- **持拍手**：第一版作为命令行参数传入（`--handedness 选手=right`），只用于区分
  inside-out / inside-in。
- **派生的球路记录**（`shots-v1`，纯派生，可随时重算）：
  - 回合 ID、拍序、角色（发球 / 接发 / 相持）；
  - 击球者、拍型、击球者球场位置；
  - 关联落点的球场坐标（没有弹跳证据时为空）；
  - 上一拍的 ID（即“来球”）；
  - 派生分类：方向（发球 T / 追身 / 外角；相持 斜线 / 直线 / 中路 / inside-out /
    inside-in）、深度区、宽度区；
  - 归一化坐标：统一成“击球者在下方”的视图，换边不影响合并；
  - 输入事件 ID、复核状态、规则版本。
- **战术查询**：条件（发球区、发球方向、来球落区、对手拍型、拍序……）→ 回应分布
  （落点热区、方向比例），输出分子、分母、排除原因、区间和支持片段。

方向术语与 F3Set 和 Match Charting Project 的标注体系对齐，方便借用公开数据。

### 现在怎么用

```sh
tennis-ai shots outputs/my-match --view human_verified --output shots.json
tennis-ai tendency outputs/my-match --participant opponent \
  --where role=return --incoming serve_side=deuce --incoming direction=wide \
  --handedness opponent=right --output return.json --map return.png
```

第二条命令回答“我在一区发外角时，他的接发球打到哪里”。结果里有方向、深度、宽度三个分布，
每一项带样本数、95% 区间和对应的击球 ID。样本少于 8 个时标为 `limited`。

前提是比赛里的击球、弹跳、拍与落点关联、回合和选手身份已经存在；`human_verified`
视图只使用人工确认过的那部分。目前这些证据主要靠人工复核产生，T3–T5 的作用就是减少这部分工作量。

### 第一版的规则和已知限制

- 方向按击球者视角归一化（击球者始终在下方）。落点在单打场地中间三分之一算“中路”；
  否则落点和击球者在中线同一侧算“直线”，不同侧算“斜线”。站在中线附近击球时这个划分比较粗。
- 发球方向把正确的发球区横向三等分：靠中线是 T，靠边线是外角，中间是追身。
  落在发球区外不给方向，也不判定为发球失误。
- 深度：底线到发球线的中点以内是“深”，到发球线是“中”，发球线到网是“浅”。
- 这些是描述性统计，不预测，也不说明因果。

接下来的建议顺序是 T2 → T3 → T6，T4 和 T5 可与 T3 并行。人工复核产生的结果同时就是
T3–T5 的训练和验证标注。

### 数据上的注意事项

1. **域匹配**：以上数据集几乎全是职业转播的高机位画面，和现在的目标场景一致，
   可以直接用于微调，一部分留作测试集。同一场比赛的片段必须整体放在训练、验证或
   测试的同一侧。
2. **仍然需要自己复核一些比赛**：公开数据集没有同时包含“球坐标 + 落点球场坐标 +
   击球者位置”的完整标注，落点误差这类门槛只能在自己复核的比赛上测。
3. **视频版权**：多数数据集只授权标注，视频来自 YouTube 或转播。只在本地用于研究，
   不提交、不再分发；每个数据集的来源、版本、校验和、许可记入 provenance。
4. **手机场景**：搁置期间不做。公开数据对手机机位的域差问题届时再评估。

## 7. 风险

- **样本量**：一场比赛里“一区外角发球”可能只有 8–15 个，单场结论很不稳。必须显示
  样本数和区间，设最小支持数，并支持多场合并。结论只描述倾向，不说因果。
- **复核工作量**：在 T3–T5 完成前，一盘大约要确认 150–250 拍。需要优先级队列和快捷操作，
  否则没人愿意用。
- **远端落点误差**：远端一个像素对应的球场距离更大，落点误差要按近端/远端分开报告。
- **转播画面的干扰**：回放、慢动作、特写会产生重复或错误的事件，T2 完成前需要人工排除。

## 8. 已确认的决定（2026-11-10）

1. 目标场景是转播/鹰眼机位视频；手机拍摄和 iOS 应用搁置，代码保留。
2. 先用公开模型加微调；自研模型是基础完成之后的长期目标（T8）。
3. 三维增强放在后面（T7）。
